# Архитектурные решения MeetPoint

Основа: [кейс MeetPoint, стр. 7–11](https://static.centraluniversity.ru/documents/events/Prod/Keisy-Khakaton-PROD-Minsk-2026.pdf#page=7) и [критерии Backend, стр. 1–2](https://static.centraluniversity.ru/documents/events/Prod/Kriterii-Khakaton-PROD-Minsk-2026.pdf).

Документ разделён на пять этапов описания системы. Их структуру выбрали для этого проекта: опубликованные критерии требуют пять этапов, но не перечисляют их названия и содержание.

## 1. Требования и ограничения

Организатор создаёт событие с интересами, получает ссылку и QR, отслеживает знакомства. Участник заполняет короткий профиль, находит людей, отправляет приглашение и обменивается контактами после принятия. Чужие контакты до согласия закрыты и для организатора. Повторный вход в том же браузере сохраняет профиль.

Объём проекта — бэкенд на FastAPI, PostgreSQL и синхронной SQLAlchemy. Проверка проводится через Swagger. Сведения о событии возвращаются в JSON; QR содержит ссылку на этот endpoint. Пользовательский интерфейс, чат, геолокация и уведомления в объём не входят.

Для демонстрации CI/CD достаточно временного развёртывания в GitHub Actions. Постоянный сервер и публичный адрес не предусмотрены.

## 2. Сценарии и API

Точный контракт генерируется из [роутеров](../app/routers) и [схем](../app/schemas.py), доступен в `/docs` и `/openapi.json`. Все пути ниже начинаются с `/api`.

| Действие | API | Существенное правило |
| --- | --- | --- |
| Начать работу | `POST /session` | Действующая cookie переиспользуется |
| Создать событие | `POST /events` | Создатель становится владельцем |
| Открыть сведения и QR | `GET /events/{event_id}`, `GET …/qr.svg` | Ответ публичный, без секретов |
| Сохранить свой профиль | `PUT /events/{event_id}/me` | Одна сессия — один профиль в событии, 3–5 интересов |
| Найти людей | `GET …/participants`, `GET …/recommendations` | Только участники события; контакты исключены |
| Познакомиться | `POST …/requests`, `GET …/requests`, `PATCH …/requests/{request_id}` | Решение принимает только получатель |
| Получить контакты | `GET …/contacts` | Принятое приглашение открывает контакт обеим сторонам |
| Посмотреть статистику | `GET …/stats` | Только владелец, только счётчики |

Приглашение переходит из `pending` в `accepted` или `skipped`. Повтор того же решения допустим; противоположное после завершения возвращает `409`. Встречное приглашение не считается согласием. Пропуск окончательный, повторного запроса для той же пары нет.

Лента фильтруется по совпадению хотя бы одного выбранного интереса. Рекомендации сортируются по числу общих тегов, затем времени создания и ID; пагинация применяется после сортировки. Списки поддерживают `limit` и `offset`.

## 3. Модель данных

Модель описана в [app/models.py](../app/models.py), её создание — в [начальной миграции](../migrations/versions/20261029_01_create_meetpoint_tables.py).

| Таблица | Назначение и связи |
| --- | --- |
| `sessions` | Хеш случайного токена и срок браузерной сессии |
| `events` | Сведения о событии, ссылка на сессию владельца |
| `tags` | Интересы конкретного события |
| `participants` | Профиль и закрытый контакт; ссылки на событие и сессию |
| `participant_tags` | Связь профилей с интересами |
| `connection_requests` | Отправитель, получатель, событие, решение и время ответа |

У профиля уникальна пара `(event_id, session_id)`, у тега — `(event_id, name)`. Связь профиля с тегом тоже уникальна. Внешние ключи защищают ссылки; сервис отдельно проверяет совпадение события у участников и интересов.

Уникальный индекс по `event_id`, `LEAST(sender_id, recipient_id)` и `GREATEST(sender_id, recipient_id)` оставляет одну запись на пару людей, включая одновременные встречные приглашения. `CHECK` запрещает запрос себе и неизвестные статусы. Индексы ленты и входящих соответствуют фильтрам API.

Отдельной таблицы знакомств нет: запись со статусом `accepted` уже хранит согласие. Поэтому `requests_accepted` и `connections_count` равны числу принятых записей, а не удвоенному числу участников.

## 4. Устройство и обоснование решений

| Решение | Где реализовано | Причина |
| --- | --- | --- |
| Синхронные обработчики и ORM | [db.py](../app/db.py), [роутеры](../app/routers) | Небольшой MVP удобно читать и отлаживать без смешивания синхронного и асинхронного доступа к БД |
| Бизнес-операции отдельными функциями | [services.py](../app/services.py) | Регистрация и приглашения читаются целиком, без дополнительных слоёв репозиториев |
| Одна `Session` БД на запрос | [db.py](../app/db.py) | Изоляция работы запросов, явный commit записи, rollback при ошибке, гарантированное закрытие |
| Анонимная браузерная сессия | [sessions.py](../app/routers/sessions.py), [dependencies.py](../app/dependencies.py) | Короткий вход без паролей; права определяет сервер, а не переданный `sender_id` |
| Отдельные публичные и закрытые ответы | [schemas.py](../app/schemas.py) | Контакт отсутствует в ленте и приглашениях даже на уровне JSON |
| SQL для рекомендаций | [services.py](../app/services.py) | Пересечение тегов считается до пагинации; результат объясняется `common_tags_count` |

Токен сессии случаен, в БД хранится SHA-256. Cookie имеет `HttpOnly`, `SameSite=Lax`, а при HTTPS — `Secure`; срок проверяется сервером. Записывающие запросы с чужим `Origin` отклоняются. API-ответы получают `Cache-Control: no-store`, параметры SQL скрыты из сообщений SQLAlchemy.

Регистрация использует PostgreSQL upsert. Он блокирует строку профиля до commit, поэтому смена тегов остаётся одной атомарной операцией. Повтор приглашения ограничивает индекс БД; ожидаемый конфликт превращается в `409`. Ответ на приглашение выполняется условным `UPDATE … WHERE status = 'pending'`, что оставляет одного победителя при одновременных противоположных решениях.

## 5. Эксплуатация, ограничения и проверка

[Dockerfile](../Dockerfile) содержит runtime и тестовую сборку; [compose.yaml](../compose.yaml) описывает приложение и PostgreSQL 17. Миграции применяются перед запуском приложения. `/health` проверяет соединение с БД, `/docs` позволяет изучить контракт. Настройки и origin берутся из [config.py](../app/config.py) и окружения.

[scripts/seed.py](../scripts/seed.py) создаёт выделенное демособытие, шесть интересов и четыре вымышленных профиля. Повторный запуск сохраняет ID профилей и готовые решения по приглашениям, обновляя демосессии. Cookie находятся в игнорируемом `.local/demo/` и не входят в репозиторий.

[CI и демонстрационный CD](../.github/workflows/ci.yml) описывают проверки с PostgreSQL, сборку Docker, миграции, запуск приложения и HTTP-сценарий [scripts/smoke.py](../scripts/smoke.py). Развёртывание живёт только в рамках job. Результаты конкретного запуска, отчёты и логи доступны во вкладке Actions. После завершения job временный стенд удаляется.

Проверки сценариев и команды получения отчёта о покрытии перечислены в [TESTING.md](TESTING.md). Отчёты формируются запуском, проценты не задаются вручную.

Личность сохраняется только в одном браузере, по умолчанию на 30 дней. После удаления cookie или истечения сессии восстановить профиль и права организатора нельзя. Контакт не подтверждается; отзыв согласия не реализован.
